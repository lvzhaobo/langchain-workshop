# 基于图的Agent编排

## 一、图结构基础概念

### 1.1 节点类型（Node）

- **Agent节点**：封装一个 LLM 调用 + 工具调用，是图的核心执行单元
- **工具节点（Tool Node）**：纯函数节点，执行确定性操作（API调用、数据处理、文件读写）
- **条件判断节点（Router/Condition Node）**：根据上游输出做路由决策，本身不产生新内容
- **人工介入节点（Human-in-the-Loop Node）**：暂停执行等待人工审批/输入后再继续
- **汇总/合并节点（Aggregator Node）**：等待多个上游分支全部到达后合并结果

### 1.2 边类型（Edge）

- **直接边（Direct Edge）**：无条件路由，上游完成即进入下游，A → B
- **条件边（Conditional Edge）**：根据上游输出动态选择下游节点，A → 如果 X 则 B，否则 C
- **动态边（Dynamic Edge）**：运行时决定目标节点，常用于不确定数量的并行分支或工具调用结果驱动的路由
- **并行扇出/扇入（Fan-out / Fan-in）**：一对多分发、多对一汇聚

### 1.3 状态设计（State）

- **状态Schema（State Schema）**：定义图中流转的数据结构，所有节点共享读写
- **状态不可变性**：每个节点返回新状态而非修改旧状态，便于回滚和审计
- **局部状态 vs 全局状态**：哪些字段全图可见、哪些仅父子节点间传递
- **状态归约器（Reducer）**：多路并行输出如何合并回主状态（追加/覆盖/自定义合并逻辑）

---

## 二、DAG 设计与执行控制（核心深化）

### 2.1 图结构设计

- **DAG 约束**：不允许循环依赖，保证执行必然终止
- **拓扑分层**：同一层的节点可并行执行，层间串行
- **依赖声明式**：声明依赖关系而非执行步骤，由引擎自动推导并行度
- **图即文档**：DAG 本身是可读的业务流程描述

### 2.2 执行控制

- **拓扑排序驱动**：引擎自动计算执行顺序，最大化并行度
- **条件路由**：在节点完成时动态决定下一个（或多个）节点
- **循环/重试**：通过条件边回指实现有限循环（需打破纯DAG约束，通常由引擎特殊支持）
- **检查点（Checkpoint）**：每步执行后自动保存状态快照，支持中断恢复
- **断点续跑**：从任意历史Checkpoint重新执行，而非从头开始
- **超时与取消**：单节点超时管理 + 全图取消信号传播

### 2.3 并行执行模型

- **数据并行**：同一节点的多个实例处理不同数据分片
- **任务并行**：不同节点在同一层并行执行（无依赖关系的节点）
- **流水线并行**：上游产出部分结果即触发下游，不等上游全部完成

## 三、Subagent 调用模式

### 3.1 调用方式

- **同步调用**：父Agent阻塞等待Subagent完成，适用于依赖结果的场景
- **异步调用**：父Agent派发任务后继续执行，结果通过回调/轮询获取
- **流式调用**：Subagent逐token/逐步骤回传中间结果，父Agent可提前介入
- **批量调用**：N个同质Subagent并行处理不同输入

### 3.2 上下文传递策略

- **全量传递**：父Agent将全部状态复制给Subagent（简单但Token开销大）
- **子集传递**：仅传递Subagent完成任务所需的最小上下文（高效但需精心设计）
- **环境继承**：Subagent继承父Agent的工具集、权限、记忆（隔离策略的权衡）
- **结果归约**：Subagent仅返回结构化结果，不暴露内部推理过程

### 3.3 隔离与安全

- **共享内存模式**：Subagent直接读写父Agent的状态空间
- **沙箱模式**：Subagent独立上下文，仅通过输入/输出接口交互
- **权限衰减**：Subagent权限 ≤ 父Agent权限，防止权限逃逸

## 四、多Agent协同模式（图上的编排范式）

### 4.1 Supervisor/Orchestrator 模式

- 一个主控Agent（Supervisor）根据任务类型将子任务路由到不同的Worker Agent
- 图中体现为：Supervisor节点 + 条件边分发到多个Worker节点 + 结果汇聚回Supervisor
- 适用场景：任务类型多样、需要中心化决策

### 4.2 顺序流水线（Sequential Pipeline）

- Agent A → Agent B → Agent C，每个节点的输出是下一个节点的输入
- 图退化为链，是最简单的DAG特例
- 适用场景：明确的多阶段处理流程（采集→清洗→分析→输出）

### 4.3 Map-Reduce 模式

- **Map阶段**：一个任务拆分为N个子任务，N个Worker并行处理（Fan-out）
- **Reduce阶段**：一个Aggregator汇总所有Worker结果，生成最终输出（Fan-in）
- 适用场景：大批量同类任务处理、文献综述、多路代码审查

### 4.4 辩论/多路采样模式

- 多个Agent独立对同一问题给出答案 → 裁判Agent综合评判选出最优解
- 图中体现为：入口节点Fan-out到多个回答者 → Fan-in到裁判节点
- 适用场景：需要多角度验证的高风险决策、代码方案选型

### 4.5 分层/嵌套Agent

- Agent内部调用另一个子图（Subgraph），形成递归嵌套结构
- 图中体现为：一个复合节点展开后是另一个完整的DAG
- 适用场景：复杂任务的模块化拆解，每层有独立的状态空间

## 五、主流实现框架

### 5.1 LangGraph（LangChain 生态）

- 核心概念：StateGraph + Node + Edge + Checkpointer
- 特点：支持条件边、循环、流式输出、Human-in-the-Loop
- 优势：生态成熟、社区活跃、与LangChain工具链无缝集成
- 适合场景：需要复杂状态管理和流式输出的图编排

### 5.2 CrewAI Flow

- 核心概念：Crew（Agent团队）+ Flow（事件驱动流程图）
- 特点：基于事件的编排，Flow通过 `@start` / `@listen` / `@router` 装饰器定义流转
- 优势：语法简洁，适合快速搭建Agent团队协作
- 适合场景：Agent角色明确、交互模式相对固定的场景

### 5.3 AutoGen（微软）

- 核心概念：GroupChat + Speaker Selection（动态发言者选择）
- 特点：对话驱动的编排，由LLM动态决定下一个发言者
- 优势：灵活性高，适合对话式多Agent交互
- 适合场景：对话式协作、非确定性流程

### 5.4 低代码/无代码平台

- **Dify / Coze**：拖拽式DAG编辑器，零代码搭建Agent工作流
- **Temporal.io**：面向长时运行任务的Workflow引擎，强一致性保证
- 优势：可视化、易观测、低门槛
- 局限：灵活性受限于平台能力

## 六、与线性/树形编排的对比

| 维度 | 线性编排（Chain） | 树形编排（Tree） | 图编排（Graph/DAG） |
|------|------------------|-----------------|-------------------|
| 结构 | A→B→C 单链 | 根→多个分支→叶 | 任意DAG，多入多出 |
| 并行 | 不支持 | 支持扇出 | 支持任意并行 |
| 汇聚 | 不支持 | 不支持 | 支持多对一汇聚 |
| 循环 | 不支持 | 不支持 | 有限支持（条件回指） |
| 复杂度 | 低 | 中 | 高 |
| 可观测性 | 极好（线性追踪） | 一般 | 需要专门的图可视化 |
| 典型框架 | LangChain Chain | 自定义递归 | LangGraph、Dify |

## 七、工程化关注点

### 7.1 可观测性

- **节点级追踪**：每个节点的输入/输出/耗时/Token消耗记录
- **图可视化**：执行路径高亮、瓶颈节点着色
- **延迟分析**：定位长尾节点，优化并行拓扑

### 7.2 容错与鲁棒性

- **单节点失败策略**：重试 N 次 / 跳过 / 降级 / 转人工
- **级联失败隔离**：一个分支失败不影响其他并行分支
- **部分成功处理**：Map-Reduce中部分Worker失败时的汇总策略

### 7.3 状态持久化

- **Checkpoint 自动保存**：每节点执行后生成状态快照
- **增量存储**：仅保存与上一快照的diff，减少存储开销
- **跨会话恢复**：从任意历史Checkpoint重建图状态

### 7.4 流式输出

- **逐节点流式**：每个节点完成后即输出中间结果
- **跨节点流式**：上游节点边产出边流向下游（降低首Token延迟）
- **混合模式**：关键节点实时推送，非关键节点批量推送

### 7.5 测试与评估

- **节点级单元测试**：单节点的输入输出断言
- **图级集成测试**：完整DAG的端到端行为验证
- **回归测试**：基于Checkpoint的确定性重放
- **评估节点**：在图中嵌入评估Agent，在线评估上游输出质量

## 8.1 开场导入（15min）— 为什么需要图编排？

### 讲解要点（PPT/白板）

**① 痛点引入（5min）**

从一个真实场景切入：
> 你要做一个代码审查 Agent：先分析 diff → 分别检查安全性、性能、代码风格（三项可并行）→ 汇总结果 → 如果发现问题则人工审核 → 生成报告

提问学员："用你们现在的写法，怎么实现？"
→ 预期答案：写一堆 if/else，回调嵌套，状态管理混乱

**② 概念建立（5min）**

在黑板上画出上面的 DAG 图：

```
                    ┌─ 安全检查 ───┐
分析diff ──→ 路由 ──┼─ 性能检查 ───┼──→ 汇总 ──→ 人工审核 ──→ 生成报告
                    └─ 风格检查 ───┘
```

点出关键概念（不要求记住，先建立直觉）：
- **节点** = 每个方框是一个 Agent/函数
- **边** = 箭头表示"完成后做什么"
- **状态** = 在节点间流转的数据包
- **并行** = 同一层的三个检查同时跑

**③ 与线性 Chain 对比（5min）**

```
线性做法：
分析 → 安全检查 → 性能检查 → 风格检查 → 汇总 → 审核 → 报告
（慢：三个检查串行，即使它们互不依赖）
```

| | 线性 Chain | 图 Graph |
|---|---|---|
| 三个检查执行方式 | 逐个串行 | 同时并行 |
| 状态管理 | 靠返回值传参 | 共享 State Schema |
| 分支逻辑 | if/else 硬编码 | 条件边声明式 |
| 修改流程 | 改代码 | 改图拓扑 |
| 可恢复性 | 需自己实现 | 内置 Checkpoint |

**关键句**：_"Chain 让你思考'步骤'，Graph 让你思考'关系'。图是 Chain 的超集——任何 Chain 都是退化成一条线的 Graph。"_

## 8.2 实验一：线性流水线（30min）— 从 Chain 到 Graph

### 讲解（5min，实验前简明交代）

**要构建的图**：

```
[计划节点] → [写作节点] → [润色节点] → END
```

**核心知识**：
- `StateGraph` 是图的容器
- `add_node(name, func)` 添加节点
- `add_edge(src, dst)` 添加边
- `set_entry_point(name)` 设置入口
- `compile()` 编译图，返回可执行对象

**关键 API 对应关系**：

| LangGraph API | 含义 |
|---|---|
| `StateGraph(StateClass)` | 创建图，指定状态结构 |
| `.add_node("name", node_func)` | 注册一个节点 |
| `.add_edge("A", "B")` | A 完成后总是执行 B |
| `.set_entry_point("A")` | 从 A 开始执行 |
| `.compile()` | 编译为可调用的 App |
| `app.invoke(initial_state)` | 传入初始状态，执行全图 |

## 8.3 实验二：条件分支（30min）— 让图学会"做选择"

### 讲解（15min）

**问题引入**：

> 上一个实验中，无论文章好坏，润色节点都会执行。但如果文章已经足够好，我们想跳过润色直接输出呢？

**核心概念**：

```
                    ┌──→ [润色节点] ──┐
[写作节点] → [质量检查] ──→              ├──→ END
                    └──→   （跳过）  ──┘
```

- **条件边** `add_conditional_edges(src, router_func, route_map)`：
  - `src`：路由的起点节点
  - `router_func`：根据 state 返回路由键（如 `"good"` / `"need_polish"`）
  - `route_map`：路由键 → 目标节点的映射

```python
# 路由函数签名（固定格式）
def router(state: ArticleState) -> str:
    """根据状态返回下一个节点的名字"""
    if "足够好" in state.get("quality_check", ""):
        return "good"      # 这个字符串映射到 route_map
    return "need_polish"

# 条件边的写法
builder.add_conditional_edges(
    "quality_checker",     # 从哪个节点出发
    router,                # 路由函数
    {
        "good": END,           # 路由键 "good" → 直接结束
        "need_polish": "polisher"  # 路由键 "need_polish" → 润色
    }
)
```

**对比线性 Chain 的分支**：

```python
# ❌ 老做法：在代码里写 if
if quality == "good":
    return final
else:
    return polish(article)

# ✅ 图的做法：声明在图结构里
builder.add_conditional_edges("checker", router, {...})
# 图本身就是"程序"，不用在图内部写控制流
```

### 动手实验（15min）

**目标**：在上一个实验的基础上，在 writer 和 polisher 之间插入质量检查节点，条件路由决定是否润色

**核心代码变更**（学员在上一个实验基础上修改）：

```python
# 新增节点
def quality_checker_node(state: ArticleState) -> dict:
    """用 LLM 评估草稿质量"""
    prompt = f"""
    评估以下文章的草稿质量，只回复 "good" 或 "need_polish"：
    
    草稿：{state['draft']}
    
    判断标准：逻辑清晰、无语法错误、表达流畅 → good
    否则 → need_polish
    """
    response = llm.invoke(prompt)
    return {"quality_check": response.content.strip()}

# 路由函数
def quality_router(state: ArticleState) -> str:
    check = state.get("quality_check", "")
    if "good" in check.lower():
        return "good"
    return "need_polish"

# 修改图的连接
builder.add_node("quality_checker", quality_checker_node)
builder.add_edge("writer", "quality_checker")        # writer → 质量检查
builder.add_conditional_edges(                       # 质量检查 → 条件分发
    "quality_checker",
    quality_router,
    {
        "good": END,                    # 好 → 直接结束
        "need_polish": "polisher"       # 需要改进 → 润色
    }
)
builder.add_edge("polisher", END)                   # 润色 → 结束
```

**学员任务卡**：

| 级别 | 任务 |
|------|------|
| ⭐ 基础 | 插入质量检查节点 + 条件路由，跑通两条路径 |
| ⭐⭐ 进阶 | 改为三路路由：`"excellent"→END` / `"good"→轻润色` / `"poor"→重写`，增加第三个路由分支 |
| ⭐⭐⭐ 挑战 | 路由函数不依赖 LLM 而用规则（如计算草稿字数 < 50 则必然重写），实现 LLM + 规则混合路由 |

**成果验收**：
- 输入"Python 入门教程" → 大概率走 `good` 跳过润色
- 输入随机乱码 → 走 `need_polish` 进入润色

## 8.4 实验三：Map-Reduce 并行（30min）— 多路 Agent 同时工作

### 讲解（15min）

**场景升级**：

> 你要从三个维度审查代码变更：安全性、性能、代码风格。这三个审查互不依赖，串行太慢。

```
                         ┌──→ [安全性审查] ──┐
[分析变更] → [分发器] ───┼──→ [性能审查]   ──┼──→ [汇总器] → END
                         └──→ [风格审查]   ──┘
```

**Fan-out / Fan-in 实现方式**：

LangGraph 的 Fan-out 有两种实现方式：
1. **Send API**（新版推荐）：返回 `[Send("node", state), Send("node", state), ...]`
2. **手动展开**（简单场景）：在分发节点中自己创建子任务列表，汇总节点等待

**本次实验使用方式2（手动展开，更直观）**：

```python
class ReviewState(TypedDict):
    diff: str              # 代码 diff
    review_assignments: list[str]  # ["安全", "性能", "风格"]
    reviews: list[str]     # 每条审查结果（Reducer: 追加）
    final_report: str      # 汇总报告

# 分发节点：创建任务列表
def dispatcher_node(state: ReviewState) -> dict:
    return {"review_assignments": ["安全性", "性能", "代码风格"]}

# 并行审查节点：每个维度独立调用 LLM
def reviewer_node(state: ReviewState) -> dict:
    # 在代码中遍历 assignments 并行调用
    # 返回所有审查结果
    pass

# 汇总节点
def aggregator_node(state: ReviewState) -> dict:
    # 将所有审查结果合并为最终报告
    pass
```

**关键知识点**：`Annotated` + 自定义 Reducer

```python
from typing import Annotated
from operator import add  # 列表追加

def review_reducer(existing: list[str], new: list[str]) -> list[str]:
    """自定义合并逻辑：追加而非覆盖"""
    return (existing or []) + new

class ReviewState(TypedDict):
    reviews: Annotated[list[str], review_reducer]  # 关键！
```

如果不加 `Annotated + Reducer`，LangGraph 默认用**覆盖**语义——后一个节点的返回会覆盖前一个节点的同名字段。加了 Reducer，每次返回的 `reviews` 会**追加**到已有列表。

### 动手实验（15min）

**目标**：实现三路并行代码审查 → 汇总

**脚手架代码**：

```python
from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, END
from concurrent.futures import ThreadPoolExecutor

# 状态：关键 — reviews 使用 Reducer 追加
class CodeReviewState(TypedDict):
    diff: str
    dimension: str         # 当前审查维度（单节点复用）
    reviews: Annotated[list[str], lambda existing, new: (existing or []) + new]
    final_report: str

# TODO: 学员实现 — 分发节点
def setup_node(state: CodeReviewState) -> dict:
    # 在节点内做并行调用
    dimensions = ["安全性", "性能", "代码风格"]
    reviews = []
    # 用 ThreadPoolExecutor 并行调用 LLM
    def review_dim(dim: str) -> str:
        prompt = f"从{dim}角度审查以下代码：\n{state['diff']}"
        return llm.invoke(prompt).content
    
    with ThreadPoolExecutor(max_workers=3) as executor:
        reviews = list(executor.map(review_dim, dimensions))
    
    # 由于 reviews 有 Reducer，每次调用会自动追加
    return {"reviews": reviews}

# TODO: 学员实现 — 汇总节点
def summary_node(state: CodeReviewState) -> dict:
    all_reviews = "\n---\n".join(state["reviews"])
    prompt = f"汇总以下三条审查意见，生成统一的代码审查报告：\n{all_reviews}"
    report = llm.invoke(prompt).content
    return {"final_report": report}

# 构建图
builder = StateGraph(CodeReviewState)
builder.add_node("reviewer", setup_node)    # 一个节点内并行三个维度
builder.add_node("summarizer", summary_node)

builder.set_entry_point("reviewer")
builder.add_edge("reviewer", "summarizer")
builder.add_edge("summarizer", END)

app = builder.compile()

# 运行
fake_diff = """
+ const userInput = req.body.input;
+ const query = `SELECT * FROM users WHERE name='${userInput}'`;
+ console.log(query);
"""
result = app.invoke({"diff": fake_diff})
print(result["final_report"])
```

**学员任务卡**：

| 级别 | 任务 |
|------|------|
| ⭐ 基础 | 补全分发和汇总逻辑，让三路审查并行跑通 |
| ⭐⭐ 进阶 | 使用 LangGraph 的 `Send` API 实现真正的图级 Fan-out（而非节点内并行），添加 `add_node` 复用同一函数三次 |
| ⭐⭐⭐ 挑战 | 增加 Reducer 逻辑，汇总时自动去重 + 按严重程度排序 |

**验收标准**：
- 一份 diff 输入，同时生成安全/性能/风格三条审查意见
- 汇总报告整合了三条意见
- 对比串行 vs 并行执行时间（三个审查串行 ~9s vs 并行 ~3s）

## 8.5 实验四：Checkpoint + Human-in-the-Loop（25min）— 状态持久化与人工介入

### 讲解（15min）

**场景**：

> 代码审查完成了，但安全审查发现了 SQL 注入——这需要人工确认是否真的存在问题，然后决定继续还是返回修改。

**核心概念**：

1. **Checkpoint（检查点）**：LangGraph 在每一步执行后自动保存状态快照
2. **中断（Interrupt）**：在特定节点前/后暂停，等待外部输入
3. **恢复（Resume）**：传入新输入从断点继续执行

```python
from langgraph.checkpoint.memory import MemorySaver

# 开启 Checkpoint
checkpointer = MemorySaver()
app = builder.compile(checkpointer=checkpointer)

# 执行时指定 thread_id 以支持多会话
config = {"configurable": {"thread_id": "review-001"}}
result = app.invoke(initial_state, config)

# 查看历史状态
for checkpoint in app.get_state_history(config):
    print(checkpoint)
```

**Human-in-the-Loop 实现**：

```python
# 方式1：在 compile 时指定中断节点
app = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["human_review"]  # 在执行 human_review 节点前暂停
)

# 执行到断点
app.invoke(state, config)  # 执行到 human_review 前自动暂停

# 获取当前状态
current = app.get_state(config)
print(current.values)  # 当前状态数据

# 人工提供输入后恢复
app.invoke(
    {"human_feedback": "SQL注入确认存在，请修复"},  # 人工输入
    config
)  # 从断点继续执行
```

### 动手实验（10min）

**目标**：在实验三的基础上增加人工审核节点，发现问题后暂停等待人工确认

```python
from langgraph.checkpoint.memory import MemorySaver

# 新增人工审核节点
def human_review_node(state: CodeReviewState) -> dict:
    """
    此节点在执行前会暂停，等待人工输入。
    人工输入通过 app.invoke({"human_decision": ...}, config) 传入
    """
    decision = state.get("human_decision", "approve")
    if decision == "approve":
        return {"human_result": "✅ 人工审核通过"}
    else:
        return {"human_result": f"❌ 人工审核驳回：{state.get('human_feedback', '')}"}

# 修改图
builder = StateGraph(CodeReviewState)
builder.add_node("reviewer", setup_node)
builder.add_node("summarizer", summary_node)
builder.add_node("human_review", human_review_node)  # 新增

builder.set_entry_point("reviewer")
builder.add_edge("reviewer", "summarizer")
builder.add_edge("summarizer", "human_review")  # 汇总 → 人工审核
builder.add_edge("human_review", END)

# 编译时指定中断点
checkpointer = MemorySaver()
app = builder.compile(
    checkpointer=checkpointer,
    interrupt_before=["human_review"]  # 在人工审核前暂停
)

# === 第一轮：执行到人工审核节点前 ===
config = {"configurable": {"thread_id": "review-session-1"}}
result = app.invoke({"diff": fake_diff}, config)

print("🔴 暂停在人工审核前，等待人工决策...")
print(f"当前汇总报告：\n{result['final_report'][:200]}...")

# === 第二轮：人工决策后恢复 ===
# 假设人工看过后发现安全审查误报，决定放行
result = app.invoke(
    {"human_decision": "approve"},
    config  # 同一个 thread_id
)

print(f"✅ 最终结果：{result.get('human_result')}")
print(f"执行历史快照数：{len(list(app.get_state_history(config)))}")
```

**学员任务卡**：

| 级别 | 任务 |
|------|------|
| ⭐ 基础 | 复制粘贴上述代码，观察断点暂停 → 恢复的完整流程，打印状态历史 |
| ⭐⭐ 进阶 | 增加条件路由：人工审核通过 → END；驳回 → 回到 reviewer 重新审查 |
| ⭐⭐⭐ 挑战 | 使用 SqliteSaver（持久化到磁盘）替代 MemorySaver，关闭程序后重新打开，用同一个 thread_id 恢复执行 |

**验收标准**：
- 肉眼看到程序"暂停"在人工审核前
- 手动传入 `human_decision` 后程序继续执行
- `get_state_history` 能看到完整的执行轨迹

## 8.7 总结与 Q&A（15min）

### 关键回顾（5min）

```
一次完整的图 Agent 开发流程：

1. 画图（白板/纸上先画 DAG 拓扑）
2. 定义 State（TypedDict，确定流转什么数据）
3. 实现节点（Agent/函数，输入 state 返回 dict）
4. 连接边（add_edge / add_conditional_edges）
5. 编译运行（compile + invoke）
6. 加 Checkpoint（需要持久化/中断恢复时）
7. 迭代优化（加节点、改路由、调整并行度）
```

### 常见踩坑总结（5min）

| 坑 | 原因 | 解法 |
|----|------|------|
| 字段被覆盖而非追加 | 没用 `Annotated` + Reducer | 给共享字段加 Reducer |
| 路由函数返回了不存在的目标 | route_map 里没有这个 key | 检查 route_map 覆盖所有路由分支 |
| 并行节点结果丢失 | 没有正确合并 state | 检查 Reducer 逻辑 |
| 恢复执行时用了新 config | thread_id 不匹配 | 用同一个 thread_id |
| `invoke` 后拿不到预期的字段 | 节点忘了返回该字段 | 在每个节点 return 中确认字段名 |
