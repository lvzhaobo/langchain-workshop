1. 共享状态定义

MultiAgentState（TypedDict）— 所有 Agent 共享同一份状态字典

字段类型写入方读取方说明
device_idstr 初始输入 Diagnosis, Execute 故障设备编号
symptomstr 初始输入 Diagnosis 故障现象描述
diagnosis_resultstr Diagnosis Agent Supervisor, Solution, Execute 故障诊断结论
solution_planstr Solution Agent Supervisor, Execute 维修处置方案
execution_recordstr Execute Agent Supervisor 巡检记录
next_actionstr Supervisor 路由函数 下一节点名称
task_historylist 每个 Agent 追加 汇总节点 已执行的任务序列

2. State 是什么？由谁设置？

State 不是 LangChain 内置的，是你定义的 Python TypedDict。StateGraph 用它作为共享数据结构的"蓝图"，每个节点读写同一个字典。

# State 是你自己定义的，不是 LangChain 预设的
class MultiAgentState(TypedDict):
    diagnosis_result: Optional[str]    # 你定义
    solution_plan: Optional[str]       # 你定义
    execution_record: Optional[str]    # 你定义
    next_action: str                   # 你定义
    task_history: list                 # 你定义

# 创建 StateGraph 时传入这个 TypedDict
wf = StateGraph(MultiAgentState)       # LangGraph 用这个结构管理状态

# 每个节点返回部分字段，LangGraph 自动合并

一句话：State 是你自己用 TypedDict 定义的 Python 字典结构。StateGraph 负责在每个节点返回后，把返回的字段合并到同一个字典里。节点的代码就是普通的"读 dict 字段 → 返回 dict 字段"——没有黑魔法。

3. 核心机制：节点返回部分状态，LangGraph 自动合并

# Diagnosis Agent — 只返回自己改的字段
def diagnosis_node(state: MultiAgentState) -> dict:
    # 读取 state["device_id"]、state["symptom"]
    diagnosis = _chat(client, prompt, system_prompt)
    return {
        "diagnosis_result": diagnosis,        # 只写这个
        "task_history": state["task_history"] + ["diagnosis"]
    }
    # LangGraph 自动把这两个字段合并回全局 state
    # device_id、symptom 等未修改的字段保持不变

# Solution Agent — 读取前一步的结果
def solution_node(state: MultiAgentState) -> dict:
    # 读取 state["diagnosis_result"] ← Diagnosis 之前写入的
    solution = _chat(client, state["diagnosis_result"], system_prompt)
    return {
        "solution_plan": solution,              # 新增字段
        "task_history": state["task_history"] + ["solution"]
    }
    # 合并后 state 同时包含 diagnosis_result + solution_plan

4. Agent 读写矩阵

  • ── 写入 ──
  • ↳ diagnosis_result
  • ↳ task_history

  • ── 读取 ──
  • ↳ diagnosis_result
  • ── 写入 ──
  • ↳ solution_plan
  • ↳ task_history

Execute Agent
  • ── 读取 ──

  • ↳ solution_plan

  • ↳ task_history

5. 完整时序流程

1

Supervisor 检查状态

读取 diagnosis_result → None。决策：路由到 Diagnosis Agent

2

Diagnosis Agent 执行

读取 device_id="EP-D-002", symptom="合闸后无法分闸" → 调用 LLM 诊断 → 写入 diagnosis_result="分闸线圈电阻异常，判断为线圈绝缘老化..." → 追加 task_history

3

Supervisor 再次检查

读取 diagnosis_result → 有值。读取 solution_plan → None。决策：路由到 Solution Agent

4

Solution Agent 执行

读取 diagnosis_result（第 2 步写入的）→ 调用 LLM 生成方案 → 写入 solution_plan="立即降负荷 → 隔离故障设备 → 测量线圈电阻..."

5

Supervisor 再次检查

diagnosis_result 有值, solution_plan 有值, execution_record → None。决策：路由到 Execute Agent

6

Execute Agent 执行

读取 diagnosis_result + solution_plan（第 2、4 步写入的）→ 生成巡检记录 → 写入 execution_record

7

Supervisor 最终检查

三个字段全部有值 → 决策：FINISH → 路由到汇总节点，输出完整报告

6. 多智能体共享状态的五种方式

方式原理适用场景本实验中对应的例子优点 / 局限
① StateGraph 共享 State 所有 Agent 共享同一个 TypedDict。每个节点读全量状态、返回部分字段。LangGraph 自动将返回字段合并到全局 state，下游节点直接从同一个字典读取上游写入的字段 多 Agent 按固定流程顺序协作 Diagnosis 写 diagnosis_result → Solution 读 → Execute 读（见 §3 读写矩阵） ✅ 直观，字段级可追溯
⚠️ 流程固化，不够灵活
② 多个 Agent 读同一个 Agent 的输出 Agent A（Diagnosis）写 diagnosis_result → Agent B（Solution）读 → Agent C（Execute）也读。同一个字段，多个下游 Agent 各自消费 一个诊断结论 → 方案 Agent 用来出方案，执行 Agent 用来记录巡检 是谁写了被多个人读？Diagnosis Agent 写了 diagnosis_result。读它的有两个：Solution Agent 用它出方案，Execute Agent 用它写巡检记录。
是谁同时读了两个人的？Execute Agent：同时读 Diagnosis 的 diagnosis_result 和 Solution 的 solution_plan		 ✅ 上游一次写入，下游多方复用
⚠️ 下游耦合到字段名
③ Supervisor 路由调度 中央调度 Agent 读取所有状态字段，根据填充情况决定调用哪个 Agent。每个 Agent 返回后，Supervisor 重新评估状态，决定下一步路由 条件分支、审批流程、需要人工介入的场景 Supervisor 检查 diagnosis_result/solution_plan/execution_record → 决定路由到哪个 Agent 或 FINISH（见 §4 时序流程） ✅ 灵活的条件路由
⚠️ Supervisor 成为单点
④ Tool Call 消息传递 Agent 调用 Tool → Tool 返回值注入到对话消息列表（messages）→ LLM 读取消息中的工具结果，决定下一步。状态不是存在字典里，而是存在对话历史中 LLM 自主决策下一步，适合探索型任务 01-agent-basic 的 ReAct 循环：LLM 调用 search_equipment → 工具结果追加到 messages → LLM 根据结果回答 ✅ Agent 间低耦合
⚠️ 消息列表膨胀
⑤ 外部存储 / MCP Agent 通过 MCP 工具读写外部系统（JSON 文件、SQLite、Redis）。数据持久化到外部，不同 Agent 甚至不同会话都可以读写 跨会话持久化、多服务协作、生产环境 Sample 2 后端 devices.json — 多个 API 端点（等同于多个 Agent）共享同一份数据文件 ✅ 跨会话、支持大容量
⚠️ 需要外部服务
