意图分类层：把自由文本压成一个枚举值

PYDANTIC STRUCTURED OUTPUT

三个字段各有各的用处

  • intent 用 Literal 卡死四个值。这是整层的输出契约——下游 RunnableBranch 只认这四个字符串。
  • device_id 是顺手做的槽位抽取（slot filling）。分类和抽取一次调用完成，比再开一次 LLM 划算。
  • reason 看着像装饰，其实是调试入口。分错了你得知道它为什么这么想，否则只能瞎调 Prompt。第 4 节那个 bug 就是靠它揪出来的。
intent_router.py · 分类 Schema
class IntentResult(BaseModel):
    intent: Literal["diagnose", "query_data",
                    "troubleshoot", "chat"] = Field(
        description="用户意图分类。diagnose=查设备状态/分析告警；"
                    "query_data=统计/分组/趋势；troubleshoot=排查故障/"
                    "搜知识库；chat=闲聊/通用问答/其他"
    )
    device_id: str = Field(default="",
        description="如果用户提到了具体设备ID则提取，格式DEV-XXXX")
    reason: str = Field(description="一句话简述分类依据")

    @field_validator("device_id")
    @classmethod
    def _only_real_device_id(cls, v: str) -> str:
        # description 里写了格式，模型照样会填型号
        v = v.strip().upper()
        return v if re.fullmatch(r"DEV-\d{4}", v) else ""
坑：Field(description=...) 是提示，不是约束。描述里明明写着"格式 DEV-XXXX"，实测输入"AAU5613 SCTP 链路中断怎么排查"时，模型把设备型号 AAU5613 当成设备 ID 填了进来。型号不是 ID，拿它去调 /devices/AAU5613 只会 404。

结构化输出真正保证的只有两件事：JSON 能解析、枚举字段落在合法值里。自由文本字段的格式它不管。凡是要拿去拼 URL、拼 SQL、拼文件路径的槽位，都得自己再校一道——这跟"永远不要相信前端传来的参数"是同一条纪律。

校验器的实测行为

模型填进来的值校验后为什么
DEV-0001DEV-0001合法，原样通过
dev-0007DEV-0007顺手规范化成大写
AAU5613（空）是型号不是 ID，拦掉
DEV-12（空）位数不对，拦掉

置空而不是抛异常，是因为 device_id 本身就是可选的——抽不到就让下游 Agent 自己去问用户。宁可少个参数，不要给个错参数。

置空之后下游反而更聪明了。实测那句 AAU5613 的输入，校验器把 device_id 清空后，排障 Agent 自己去查了一下、发现查不到，于是在回答里写道："设备 AAU5613 在系统中未注册（可能是型号标识而非实际设备 ID）"，然后照样基于知识库给出了完整方案。把不确定性明确地传下去，比伪造一个确定值要好。

四类意图的边界怎么划

Prompt 里给每类配了真实例句而不是抽象定义。"统计告警数"这种抽象说法模型理解不了边界，"告警设备有几台""华为和爱立信各多少"这种例句才能划清 query_data 和 diagnose 的界。

diagnose · 单台设备的状态 query_data · 跨设备的聚合 troubleshoot · 要方法不要数据 chat · 前三类都不是
最难划的那条线在 diagnose 和 query_data 之间。"DEV-0001 有几条告警"是查一台设备（diagnose），"告警设备有几台"是跨设备聚合（query_data），中文里两句话长得很像。区分的诀窍是看聚合的单位：算一台设备内部的东西归 diagnose，算设备之间的东西归 query_data。这条线画不清，8 条用例里至少错 2 条。

无工具不是 Agent
课堂上最容易翻车的一行：不要用 create_react_agent

如果 _make_agent 里写的是 create_react_agent，配上 ChatPromptTemplate 的 ("placeholder", "{agent_scratchpad}")，四条通道全都跑不起来，一律抛： 
ValueError: variable agent_scratchpad should be a list
of base messages, got  of type <class 'str'>
根因是两套模板体系撞了：ReAct 靠提示词文本驱动，它的 scratchpad 是一段 Thought/Action/Observation 拼接出来的字符串，必须配字符串模板 PromptTemplate；而 ChatPromptTemplate 的 placeholder 要求填进来的是 message 列表。

这个报错最坑的地方是它既不提 ReAct 也不提模板类型，只说"给了个 str"，很难从字面反推回"你该换个 agent 构造函数"。
intent_router.py · Agent 工厂
# 四个通道共用的输出约束：模型默认爱在 markdown 里撑 emoji
_OUTPUT_STYLE = "\n\n输出要求：不要使用 emoji 和装饰符号，用纯文本陈述。"

def _make_agent(tools: list, system_prompt: str) -> AgentExecutor:
    prompt = ChatPromptTemplate.from_messages([
        ("system", system_prompt + _OUTPUT_STYLE),
        ("human", "{input}"),
        ("placeholder", "{agent_scratchpad}"),
    ])
    agent = create_tool_calling_agent(llm, tools, prompt)
    return AgentExecutor(agent=agent, tools=tools,
        max_iterations=8, handle_parsing_errors=True)

为什么 chat 通道不套 Agent

Agent 的全部价值在于那个循环：选工具 → 看结果 → 再决定下一步。零工具就没有循环可言，套一层 AgentExecutor 只是白多一轮空转。

更实际的问题是：给 create_tool_calling_agent 传空 tools 列表，底层会调 llm.bind_tools([])，部分 OpenAI 兼容网关收到空的 tools 数组会直接报错。

chat 通道 · 一条普通链就够
chat_prompt = ChatPromptTemplate.from_messages([
    ("system", """你是 5G 基站运维平台助手……
引导用户使用正确的表述来触发诊断、问数、排障功能。
回答简洁友好，不超过 100 字。""" + _OUTPUT_STYLE),
    ("human", "{input}"),
])
chat_chain = chat_prompt | llm | StrOutputParser()
这条通道的实测耗时是 3.0 秒，troubleshoot 是 17.6 秒。差距不只来自工具调用次数，也来自"要不要走 Agent 循环"。一句"你好"如果被塞进全能 Agent，模型得先纠结一遍"我要不要查设备"——那是纯粹的浪费。不是所有请求都值得一个 Agent。
顺手治了个显示问题：模型默认喜欢在回答里堆 emoji 和 markdown 表格，课堂投屏时很吵。四个通道的 system prompt 末尾统一追加一段 _OUTPUT_STYLE 就治住了——统一追加，而不是四处各写一遍，这也是 _make_agent 这个工厂函数存在的意义之一。

RunnableBranch：分发、兜底、别每次重建

DISPATCH & FALLBACK
intent_router.py · 路由链
# 建一次就好：RunnableBranch 无状态，每次请求重建是白花开销
router_chain = RunnableBranch(
    (lambda x: x["intent"] == "diagnose",
     lambda x: diagnose_agent.invoke(x)["output"]),
    (lambda x: x["intent"] == "query_data",
     lambda x: query_data_agent.invoke(x)["output"]),
    (lambda x: x["intent"] == "troubleshoot",
     lambda x: troubleshoot_agent.invoke(x)["output"]),
    (lambda x: x["intent"] == "chat",
     lambda x: chat_chain.invoke(x)),
    lambda x: chat_chain.invoke(x),  # 兜底
)
为什么 chat 分支和兜底要写两遍——看着重复，守的却是两种不同情况。前者是模型正常返回了 chat；后者是模型返回了四个枚举值之外的东西。Literal 加 PydanticOutputParser 已经拦掉大部分越界值，但解析器也可能被绕过（比如换个模型、改了 Prompt）。RunnableBranch 没有兜底分支时会直接抛异常，一个入口的服务不该因为分类器打了个嗝就 500。

注意那个 dict 是怎么攒出来的

路由的判断条件读的是 x["intent"]，而各通道 Agent 读的是 x["input"]。两个 key 同在一个 dict 里往下传：_build_input() 先放 input，route() 再补 intent。少了后者，RunnableBranch 第一个 lambda 就 KeyError。

和 3.8 那套关键词路由对着看

3.8 的分发层里也有个"路由"，但它是 20 行的关键词 dict 匹配。两者放一起，正好是同一个问题的两种答法。

维度3.8 关键词匹配3.1 语义分类
延迟<1ms1~2s
成本零一次 LLM 调用
新说法不认识就漏能泛化
可解释命中哪个词很清楚靠 reason 字段
改一条会不会带崩别的会不会
3.8 那个路由 bug 正是"为什么需要 3.1"的反面教材。关键词 dict 的迭代顺序就是匹配优先级，命中即 break。"帮我看下华为有多少告警设备"因为"告警"排在"多少"前面，被判成了 diagnose。

关键点是：把顺序调对，第 6 条输入照样会错。"统计一下 DEV-0001 的告警历史"里"统计"在前，于是又被判成 query_data，可它明明是查单台设备。关键词法的问题不在于哪条规则写错了，而在于"一句话里出现了哪个词"跟"这句话什么意思"之间本来就没有稳定映射。加规则只是把错误挪个位置。
但也别急着把关键词法一棍子打死。工业界常见的做法是两级：先用关键词/正则拦住那些高置信度的固定说法（比如工单系统固定发来的 [ALARM] 前缀），走零延迟快路；剩下的自由文本才交给 LLM 分类。既省了大部分调用，又保住了泛化能力。3.8 的问题不是用了关键词，而是只有关键词、且没有兜底到语义分类。
EVL

准确率 7/8 的那次，错的是标注

MISLABELED GROUND TRUTH

现象

脚本跑 8 条用例统计准确率。改造前无论跑几次，结果永远是 7/8，而且永远是同一条不一致：

改造前的实测输出
用户: 帮我看下华为有多少告警设备
预期意图: diagnose
意图: query_data | 设备: 无
原因: 用户询问华为的告警设备数量，属于统计查询
结果: 不一致（预期 diagnose）

意图识别准确率: 7/8 (88%)

三个信号说明模型没错

  • reason 写得清清楚楚："询问数量，属于统计查询"——这个理由站得住。
  • Prompt 里 query_data 的例句本来就有一条"告警设备有几台"，跟这句几乎同构。
  • 这句话确实是跨设备聚合（华为一共几台），符合上一节说的那条边界。

所以问题在测试用例的标签上：("diagnose", "帮我看下华为有多少告警设备") 这条标注写错了。改成 query_data 之后，准确率是 8/8。

标注错误比模型错误危险得多，因为它伪装成模型的锅。模型错了，你去调 Prompt——但这次你怎么调都调不好，因为"正确答案"本身是错的。更糟的是它会指引你把 Prompt 往错的方向改：为了让模型把这句判成 diagnose，你可能会在 Prompt 里加一句"提到'看下设备'的归 diagnose"——然后真正的统计类输入开始成批出错。一次错误的标注，能引出一串错误的修复。
更隐蔽的一层：完成标准把问题盖住了。原来的验收线写的是"准确率 ≥ 75%"，而 7/8 = 88%，达标。于是这个 bug 在"实验已通过"的状态下安静地躺着。

阈值型验收标准都有这个毛病——它只告诉你"够不够"，不告诉你"哪一条错了、错得合不合理"。所以现在的完成标准提到了 ≥ 87.5%（最多错 1 条），并且要求逐条看 reason。

可以带走的三条习惯

习惯为什么
让分类器输出理由没有 reason，这个 bug 就得靠人肉猜。多花几十个 token 买一个调试入口。
看到"不一致"先查标注顺序反了会浪费一整个下午。先问"标准答案对吗"，再问"模型错在哪"。
评测集要有人复核标注是人写的，人会错。尤其是这种边界模糊的语义分类，标注者自己都可能拿不准。
顺带一个巧合：3.8 的关键词路由把这同一句话也判错成了 diagnose。两个实验、两套完全不同的机制，在同一句话上栽了跟头——说明这句话确实处在 diagnose 和 query_data 的边界地带。这种天然的边界样例，比随手编的用例值钱得多，值得单独留一份。

平台挂了不能让 Agent “看不出来”

工具函数最容易随手写成这样：

except Exception as e:
    return f"查询失败：{e}"   # 看着很耗健壮，实际上是个坑

问题不在于它把异常吞了，而在于它把异常吞成了一句 LLM 能继续往下编的话。平台没起时，Agent 不报错、不中断，它拿着“查询失败”照样产出一份格式完整、看着挺专业的诊断报告——里面的设备型号、IP、告警级别全是编的。静默产出胡编结果比直接崩溃更危险，因为你根本看不出它在编。

所以降级要分三档，三档对 LLM 说的话完全不同：

档位数据源给 LLM 的信号
1平台 API（:8000）实时数据，直接用
21.1 的 devices.json可用，但末尾明确标注「本地快照」
3都没有“请勿基于推测作答，直接说明数据不可用”

第二档能成立的前提是：平台 API 读的就是这份 devices.json，降级前后数据完全一致。如果兜底里随手编一台“华为 AAU5613 / alarm”，学员开着平台查到 running、关了平台又看到 alarm，只会以为自己环境坏了——兜底数据必须和主数据同源，否则兜底本身就成了新的 bug 源。

第三档那句“请勿基于推测作答”不是客套。工具返回值是直接拼进上下文给模型看的，它就是一次 Prompt 机会——你在这里说得多确定，模型就少编多少。

值得往深处想的三个问题

  • 多轮对话里的意图怎么切：第一句"查下 DEV-0001"（diagnose），第二句"这个告警怎么修"（troubleshoot）。第二句没有主语，单看它模型不知道"这个"指什么。要把对话历史喂给分类器——但历史喂多少？喂全了 token 涨、还容易被前文带偏。
  • 这一次分类调用值不值：它给每个请求加了 1~2 秒。可以换小模型、可以缓存高频问法、可以像上面说的加一层关键词快路。也可以反过来问：能不能不分类，直接把四套工具全挂给一个 Agent 让它自己选？——那就退回 1.6 了，代价是 Prompt 膨胀、工具选错、以及"你好"也要走全套推理。
  • 降级策略比兜底分支更重要：现在解析失败就全走 chat。但"分不清"和"该闲聊"是两件事——更好的做法是反问用户（"你是想查这台设备的状态，还是想知道怎么修？"），把歧义交回给唯一真正知道答案的人。这跟 3.4 的 HITL 是同一个思路。
还有个顺手的收获：意图识别天然就是一层输入分类器，位置正好在所有业务逻辑之前。3.5 要做的输入护栏（拦越权、拦注入）完全可以搭在这里——给 intent 多加一个 reject 枚举值，越权请求连通道都进不去。一层设计得当的分类器，往往能顺带解决它本来没打算解决的问题。
