# Lab 21 · 意图识别 + 路由 Agent —— 一句话自动分发到正确通道

> 前面几组 lab 已经搭出多个 Agent 能力：诊断设备、查询数据、排障建议、通用对话。但用户要说清楚"我到底要什么"——"查设备状态"才能调诊断，"帮我统计"才能调问数。本实验给平台加一层意图识别：用户说一句自然语言，系统自动判断意图、自动路由到正确的 Agent。从此用户不需要知道后端有几个 Agent。

---

## 🎯 实验目标

- 用 LLM + Pydantic 实现意图分类器，将用户输入分到四个通道之一
- 用 RunnableBranch 根据分类结果路由到对应的处理 Agent
- 四个通道（诊断/问数/排障/聊天）各自挂不同的工具集和 System Prompt
- 接入平台：一个入口 `/agent/intent-router`，用户不用选"用哪个 Agent"

---

## 📦 标准路径

### 第零步：确认三个前置依赖

本实验把前面几组 lab 的东西全串上了，所以三个依赖缺一不可：

```bash
# 1) 向量库索引必须已生成（troubleshoot 通道要搜它）
ls ../12-FAISS向量库/faiss_index/

# 2) 设备数据必须存在（diagnose 通道直接读它，query_data 通道把它灌进 SQLite）
ls data/devices.json
```

三个里缺哪个，对应的通道就会降级或报错，**但意图识别那一层照样能跑**——这也是分层的好处：分类器不依赖任何业务数据。

其中第 1 项（平台服务）**没起也能跑**：设备类工具会自动降级去读第 3 项的 `devices.json`，输出末尾会多一行「数据来源：本地快照，平台 API 未启动」。两者同源，数据完全一致。只有两边都拿不到时，工具才返回明确的取数失败，并且会在返回值里直接告诉 LLM「请勿基于推测作答」——详见下面「取数降级的三档」。

### 第一步：定义意图分类 Schema

```python
from pydantic import BaseModel, Field
from typing import Literal

class IntentResult(BaseModel):
    intent: Literal["diagnose", "query_data", "troubleshoot", "chat"] = Field(
        description="用户意图分类"
    )
    device_id: str = Field(default="", description="如果提到设备ID则提取")
    reason: str = Field(description="分类依据")

    @field_validator("device_id")
    @classmethod
    def _only_real_device_id(cls, v: str) -> str:
        v = v.strip().upper()
        return v if re.fullmatch(r"DEV-\d{4}", v) else ""
```

> **为什么需要那个 validator**：`Field(description=...)` 只是写给模型看的一句提示，不是约束。实测输入“AAU5613 SCTP 链路中断怎么排查”时，模型会把设备**型号** `AAU5613` 当成设备 ID 填进来。拿它去调 `/devices/AAU5613` 只会 404。结构化输出保证的是“JSON 能解析、枚举值合法”，不保证自由文本字段真的符合你描述里提的格式。凡是要拿去拼 URL、拼 SQL 的槽位，都得自己再校一道。

四种意图有明确的定义边界：
- **diagnose**：查询设备状态、查看告警。"DEV-0001 状态怎么样""这台设备有什么告警"
- **query_data**：统计、分组、排序。"告警设备有几台""华为和爱立信各多少"
- **troubleshoot**：排障、找方法。"AAU5613 SCTP链路中断怎么修""这个告警怎么排查"
- **chat**：上述三类之外的任何输入。"你好""你能做什么""今天天气"

### 第二步：LLM 意图分类

```python
from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.prompts import ChatPromptTemplate

parser = PydanticOutputParser(pydantic_object=IntentResult)

intent_prompt = ChatPromptTemplate.from_template("""你是 5G 基站运维平台的意图识别模块。分析用户输入，归类。

意图定义：
- diagnose：查设备状态、看告警详情
- query_data：统计数据、分组对比、Top N
- troubleshoot：排查故障原因、搜索处理方法
- chat：闲聊、自我介绍、不在前三种的其他输入

{format_instructions}

用户输入：{input}""")

intent_chain = intent_prompt.partial(
    format_instructions=parser.get_format_instructions()
) | llm | parser
```

### 第三步：构建四个通道的处理 Agent

参考 [intent_router.py](./intent_router.py) 中的 `_make_agent` 工厂函数。核心区别：

- diagnose Agent：3 个工具（查设备 + 列设备 + 查告警），Prompt 强调“基于设备实际数据诊断”
- query_data Agent：1 个工具（text-to-SQL），Prompt 强调“翻译为 SQL → 执行 → 解读结果”
- troubleshoot Agent：2 个工具（查设备 + 搜知识库），Prompt 强调“先查设备、再搜知识库、综合给出排查步骤”
- chat 通道：**不用 Agent**，一条 `prompt | llm | StrOutputParser()` 的普通链

两个容易踩的坑：

> **一、用 `create_tool_calling_agent`，不要用 `create_react_agent`**。ReAct 靠提示词驱动，它要求 `agent_scratchpad` 是一个**字符串**（Thought/Action/Observation 拼接），必须配字符串模板 `PromptTemplate`。如果你用 `ChatPromptTemplate` 的 `("placeholder", "{agent_scratchpad}")`，它要求值是 message 列表 —— 两者撑不到一起，一跑就报 `ValueError: variable agent_scratchpad should be a list of base messages, got  of type <class 'str'>`。这个报错不提 ReAct 也不提模板类型，很难从字面反推回根因。

> **二、chat 通道不要套 Agent**。Agent 的价值在于“选工具 → 看结果 → 再决定”的循环。零工具就没循环，套一层 `AgentExecutor` 只是白多一轮空转；而且给 `create_tool_calling_agent` 传空 tools 列表，`bind_tools([])` 在部分 OpenAI 兼容网关上会直接报错。

### 第四步：RunnableBranch 路由

```python
from langchain_core.runnables import RunnableBranch

router = RunnableBranch(
    (lambda x: x["intent"] == "diagnose",
     lambda x: diagnose_agent.invoke(x)["output"]),
    (lambda x: x["intent"] == "query_data",
     lambda x: query_data_agent.invoke(x)["output"]),
    (lambda x: x["intent"] == "troubleshoot",
     lambda x: troubleshoot_agent.invoke(x)["output"]),
    (lambda x: x["intent"] == "chat",
     lambda x: chat_chain.invoke(x)),
    lambda x: chat_chain.invoke(x),  # 兜底
)
```

注意两点：

- **路由链建一次就好**，写在模块层级。`RunnableBranch` 本身无状态，每次请求重建是白花开销。
- **`chat` 分支写了，兜底也要写**。看着重复，但两者守的是不同情况：前者是模型正常返回 `chat`，后者是模型返回了四个枚举值之外的东西。`RunnableBranch` 没有兜底分支时会直接抛异常。

### 第五步：端到端测试

```bash
python intent_router.py
```

脚本自动跑 8 条用例，覆盖四种意图各 2 条，统计意图识别准确率。

> **看到“不一致”先别改模型，先查标注**。这份用例里有一条“帮我看下华为有多少告警设备”，它带着“看下设备”的外壳，但要的是**数量**，属于 `query_data`。早期版本把它标成了 `diagnose`，于是准确率永远卡在 7/8，看起来像模型不够准，实际是评测集错了。**标注错误比模型错误难发现得多**，因为它伪装成模型的锅；而且当时的完成标准写的是“≥ 75%”，7/8 刚好达标，把问题盖住了。看 `reason` 字段就是为了这个——它会告诉你模型为什么这么判。

### 第六步：接入平台

在 `server.py` 中新增统一入口：

```python
from intent_router import route

@app.route("/agent/intent-router", methods=["POST"])
def intent_router():
    """统一 Agent 入口——自动意图识别 + 路由"""
    data = request.get_json()
    user_input = data.get("message", "").strip()
    if not user_input:
        return jsonify({"reply": "请输入问题"}), 400

    result = route(user_input)
    return jsonify({
        "reply": result["reply"],
        "intent": result["intent"],
        "label": result["label"],
        "elapsed": result["elapsed"],
    })
```

前端展示意图标签：

```javascript
const data = await resp.json();
// 先显示意图标签，再显示回答
showIntentBadge(data.label);  // "[诊断分析]" / "[数据查询]" 等
showReply(data.reply);
```

## 🏗️ 进阶挑战

### 1. 混淆边界测试

构造 5 条"歧义"输入——既能理解为 diagnose、也能理解为 troubleshoot。比如"DEV-0001 告警了"——是想查告警内容（diagnose）还是想排障（troubleshoot）？观察分类器的选择，调整 Intent 定义中的边界条件。

### 2. 多轮对话中的意图切换

同一段对话中，用户第一条是 diagnose（"查下 DEV-0001"），第二条是 troubleshoot（"这个告警怎么修"）。分类器能把第二条正确切换吗？给分类器加上对话历史上下文试试。

### 3. 降级策略

如果分类器置信度低于阈值（如 Pydantic 抛异常、或 intent 字段为空），怎么降级？当前代码的兜底是"全都走 chat"。更好的降级策略是什么？

#### 取数降级的三档（代码里已经实现了，对照着看）

工具函数最容易随手写成 `except Exception as e: return f"查询失败：{e}"`。问题不在于它吞了异常，而在于**它把异常吞成了一句 LLM 能继续往下编的话**——平台没起时 Agent 不报错、不中断，它拿着"查询失败"照样产出一份格式完整的诊断报告，里面的型号、IP、告警级别全是编的。**静默产出胡编结果比直接崩溃更危险，因为你根本看不出它在编。**

所以 `query_device` / `list_devices` / `get_alarms` 都改成了三档，三档对 LLM 说的话完全不同：

| 档位 | 数据源 | 给 LLM 的信号 |
|------|--------|--------------|
| 1 | 平台 API（:8000） | 实时数据，直接用 |
| 2 | 本地 `devices.json` | 可用，但末尾标注「数据来源：本地快照」 |
| 3 | 都拿不到 | **"请勿基于推测作答，直接说明数据不可用"** |

两个关键点：

- **兜底数据必须和主数据同源**。平台 API 读的就是这份 `devices.json`，所以降级前后数据完全一致。如果兜底里随手编一台"华为 AAU5613 / alarm"，学员开着平台查到 `running`、关了平台又看到 `alarm`，只会以为自己环境坏了——兜底本身就成了新的 bug 源。
- **第三档那句话不是客套**。工具返回值是直接拼进上下文给模型看的，它就是一次 Prompt 机会，你在这里说得多确定，模型就少编多少。

lab 22 / lab 23 / lab 24 用的是同一套降级逻辑（`_local_api()` 会把平台的筛选参数在本地重放一遍，保证降级前后语义一致）。

## ⚠️ 常见问题

| 问题 | 原因 | 解决方法 |
|------|------|---------|
| 报 `agent_scratchpad should be a list of base messages, got str` | 用了 `create_react_agent` 配 `ChatPromptTemplate` 的 placeholder | 换成 `create_tool_calling_agent`（详见第三步的坑一） |
| 分类器总是归到 chat | Intent Prompt 中其他三种定义不够清晰 | 在 Prompt 中加反例——"'DEV-0001 状态'不是 chat，是 diagnose" |
| device_id 提取出了型号（如 AAU5613） | `Field(description=...)` 只是提示不是约束，写了“格式 DEV-XXXX”也拦不住 | 加 `field_validator` 用正则校一道，不合格式的置空 |
| RunnableBranch 报 KeyError | lambda 中访问的 key 不存在 | 确保 `_build_input` 构造的 dict 包含 `intent` 字段 |
| 问数 Agent 跑不通 | lab 20 的 SQLite 没有正确初始化 | 确认 `_get_sql_db()` 能加载 devices.json |
| 排障通道返回“知识库检索失败” | lab 12 的 `faiss_index/` 不存在 | 先回 lab 12 把向量库建出来 |
| 回答末尾出现「数据来源：本地快照」 | 不是 bug，降级生效了：平台服务没启 | 想用实时数据就把 localhost:8000 跑起来 |
| 回答里说“取数失败” | 平台没启**且**本地 `devices.json` 也读不到 | 确认 `data/devices.json` 存在 |
| 模型输出一堆 emoji 和装饰符号 | 默认爱写 markdown 花活 | 在 system prompt 末尾统一追加输出约束（代码里的 `_OUTPUT_STYLE`） |
