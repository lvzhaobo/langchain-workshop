## 📦 模式一：Map-Reduce（并行扇出 → 汇总）

### 场景

"DEV-0001 退服了，全面排查"——这个任务天然可以拆成三个独立子任务：
1. 查设备当前状态（调平台 API）
2. 搜排障知识库（FAISS）
3. 拉历史告警记录（平台 API）

三件事互不依赖——为什么串行等？同时发、谁先回来先用谁、最后汇总。

### Graph 结构

```
        ┌───────────┐
        │  Splitter  │  LLM 把大任务拆成 N 个子任务
        └─────┬─────┘
              │
    ┌─────────┼─────────┐
    ▼         ▼         ▼
┌──────┐ ┌──────┐ ┌──────┐
│Worker│ │Worker│ │Worker│  Send API 并行执行
│  A   │ │  B   │ │  C   │
└──┬───┘ └──┬───┘ └──┬───┘
   │        │        │
   └────────┼────────┘
            ▼
      ┌───────────┐
      │  Reducer   │  汇总三路结果 + LLM 综合分析
      └───────────┘
```

### 关键代码

```python
from langgraph.constants import Send

def continue_to_workers(state):
    """返回 Send 列表 → LangGraph 自动并行"""
    tasks = state["sub_tasks"]
    return [Send("map_worker", {**state, "current_task": t}) for t in tasks]

graph.add_conditional_edges("splitter", continue_to_workers, ["map_worker"])
```

`Send` 是 LangGraph 的并行原语——不需要 `asyncio`、不需要手写线程池。

## 📦 模式二：Iterative Loop（循环精炼）

### 场景

第一次诊断结论：置信度 0.5。"可能是 SCTP 配置问题，但也可能是硬件故障。"——这个结论没法用。

应该让 Agent 回退到 detector、重新获取数据（比如查更详细的接口统计）→ 再次诊断 → 还不够？再来一轮。直到置信度达标或达到最大循环次数。

### Graph 结构

```
Detector ──→ Diagnoser ──→ [置信度检查]
                ↑               │
                │     < 0.7     │ ≥ 0.7
                └───────────────┘
                        │       达最大次数
                        ▼          │
                    Decider ←──────┘
```

一条回退边，一个阈值判断——不需要改任何 Node 的实现。

### 关键代码

```python
def loop_router(state) -> Literal["detector", "decider", "__end__"]:
    score = state.get("confidence_score", 0)
    loops = state.get("loop_count", 0)

    if score >= 0.7 or loops >= 3:
        return "decider"       # 达标或达到上限 → 继续
    return "detector"          # 不够 → 回退重来
```

## 📦 模式三：Peer Mesh（去中心化，Agent 互相调用）

### 场景

不是所有排障流程都是固定的。"这个告警我见过，直接跳到处置""诊断结果不确定，让 detector 帮忙再查一下""处置完了，回去验证一下设备状态是否恢复"。

没有 Supervisor。每个 Agent 自己决定下一个叫谁——就像运维团队里同事之间直接喊话，不需要每次经过主管。

### Graph 结构

```
   检测 ←──→ 诊断
    ↕        ↕
   处置 ←──→ 决策
    ↗    ↖
  每个边都是双向的——
  任何 Agent 可以调任何其他 Agent
```

### 关键代码

```python
# 每个节点完成后走同一个 router，router 根据状态决定下一步
graph.add_conditional_edges("detector", peer_router, {
    "diagnoser": "diagnoser",  # 正常流程
    "decider": "decider",      # 跳过诊断（已知问题）
    "executor": "executor",    # 直接处置
})

graph.add_conditional_edges("diagnoser", peer_router, {
    "detector": "detector",    # ← 回退请求更多数据
    "decider": "decider",
})
# ... 每个节点都有多种出口
```

## 🏗️ 进阶挑战

### 1. Map-Reduce 的动态拆分

当前 Splitter 是手工写死三个子任务。改为 LLM 动态拆分——用户输入一句话，LLM 自己判断"这个任务该拆成哪几个子任务、每个子任务调什么工具"。

### 2. Loop 的可变回退目标

当前回退只到 detector。实际可能只需要回退到 diagnoser（换一组搜索关键词重新搜）。增加一个判断：回退到哪个节点取决于"缺什么信息"。

### 3. Mesh 的调用收敛

当前 Mesh 可能无限循环。加上收敛机制——每个 Agent 记录自己被调了几次，超过阈值时自动路由到 executor 强制结束。

## ⚠️ 常见问题

| 问题 | 原因 | 解决方法 |
|------|------|---------|
| Send 不并行执行 | 版本——`Send` 是 LangGraph 0.2+ 才稳定的 API | `pip install langgraph>=0.2` |
| Loop 不回退 | `loop_router` 返回值与目标 dict 不匹配 | 确认 `{"detector": "detector"}` 的映射正确 |
| Mesh 循环爆栈 | Agent 之间互相调用陷入死循环 | 限制 `max_iterations` 或加 step counter |
| Reducer 结果为空 | Worker 返回的 state 未通过 `parallel_results` 合并 | 确认 `operator.add` 的 Annotated 声明 |
