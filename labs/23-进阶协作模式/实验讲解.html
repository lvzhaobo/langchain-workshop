核心演进逻辑

本实验的核心哲学

Agent 是积木，Graph 的边决定协作模式。三种新模式全部复用 3.2 的 detector / diagnoser / decider / executor 节点实现，一行 Agent 逻辑都不重写——只改 add_edge / add_conditional_edges 的连法。State 上新增了三组字段支撑新模式：sub_tasks + parallel_results（Map-Reduce 用）、loop_count + confidence_score + history_log（Loop 用）。

M-R

模式一：Map-Reduce — 并行扇出，汇总收拢

splitter → Send × N → map_worker → reducer

场景

「DEV-0001 退服了，全面排查」——这个任务天然可拆成三个互不依赖的子任务：查设备状态（平台 API）、搜排障知识库（FAISS）、拉历史告警（平台 API）。三件事互不依赖，为什么要串行等？同时发、各自跑、最后汇总。

Send：LangGraph 的并行原语

  • 路由函数返回 Send 对象列表，LangGraph 就自动并行执行——不需要 asyncio、不需要手写线程池
  • 每个 Send 携带一份独立的 State 副本（塞进各自的 current_task），Worker 之间互不干扰
  • Worker 只返回 {"parallel_results": [...]} 增量，靠 operator.add reducer 自动合并三路结果——这就是 3.2 学过的 Reducer 在并行场景的真正用武之地

本实验的三个 Worker 分工

check-device 查设备实时状态 · search-kb 搜 FAISS 知识库 · check-history 拉历史告警。每个 Worker 执行完还会让 LLM 提炼一段不超过 100 字的关键发现，Reducer 最后综合三路证据链输出诊断方案。

适合场景

可拆分的独立子任务。耗时特点：取决于最慢的那个 Worker，而不是三者之和。

模式二：Iterative Loop — 结果不够好就回退重来

confidence_checker · loop_router · 阈值 0.7 · 上限 3 轮

场景

第一次诊断结论：「可能是 SCTP 配置问题，但也可能是硬件故障」，置信度 0.5——这个结论没法用。应该让流程回退到 detector 重新取数（比如查更详细的接口统计）→ 再次诊断 → 还不够？再来一轮。直到置信度达标，或触发最大循环次数保底。

实现拆解：一个新节点 + 一条回退边

  • checker 节点：让 LLM 从诊断文本里提取 0-1 的置信度分数（解析失败兜底 0.5），同时 loop_count + 1，并把每轮结论追加进 history_log
  • loop_router：score ≥ 0.7 或 loops ≥ 3 → 放行去 decider；否则返回 "detector" 回退重来
  • 四个业务节点一行没改——循环能力完全由边和阈值实现

两个保底设计（生产必备）

MAX_LOOPS = 3 防止无限循环烧钱；达上限强制放行而不是报错终止——置信度不高也要给出"当前最优解"，比空手而归有用。适合场景：首次诊断不确定、需要多轮收敛的任务。耗时特点：回退一次就多一轮完整的检测+诊断。

loop_router() — 回退还是放行
MAX_LOOPS = 3
CONFIDENCE_THRESHOLD = 0.7

def loop_router(state):
    score = state.get("confidence_score", 0)
    loops = state.get("loop_count", 0)
    if score >= CONFIDENCE_THRESHOLD:
        return "decider"   # 达标 → 继续
    if loops >= MAX_LOOPS:
        return "decider"   # 满 3 轮强制放行
    return "detector"      # 不够 → 回退重来

graph.add_conditional_edges("checker",
    loop_router, {
    "decider":  "decider",
    "detector": "detector",  # 回退边
    "__end__":  END})

模式三：Peer Mesh — 没有 Supervisor，Agent 互相调用

peer_router · 全互联条件边 · 去中心化协作

场景

不是所有排障流程都固定：「这个告警我见过，直接跳到处置」「诊断结果不确定，让 detector 帮忙再查一下」「处置完了，回去验证设备是否恢复」。没有中央调度者——就像运维团队里同事之间直接喊话，不用每件事都经过主管。

和 Supervisor 的本质区别

  • Supervisor（3.2）：所有节点执行完都回到同一个中心重新决策，路由逻辑集中在一处
  • Mesh：每个节点都挂多个出口——detector 可以去 diagnoser / decider / executor，diagnoser 可以回退 detector，executor 处置完还能回 detector 验证
  • 本实验用共享的 peer_router 模拟"节点自主决策"：诊断文本里出现「不确定」「需要更多信息」时自动回调 detector 补数据

代价：灵活是双刃剑

互调没有中心管控，可能无限循环爆栈。本实验用 step_count（数 messages 条数）限制回退时机；进阶挑战 3 要求你实现更完善的收敛机制——每个 Agent 记录被调次数，超阈值强制路由到 executor 收尾。适合场景：非固定流程；耗时取决于跳转次数。

完成标准

  • Map-Reduce：同一任务拆为 ≥3 个子任务并行执行，Reducer 成功汇总
  • Loop：置信度 < 0.7 时自动回退，达阈值或 3 次上限后停止
  • Mesh：节点跳转不限于固定顺序——可从 diagnoser 直接跳到 executor
