LAB 3.5 · 能不能走 安全护栏

HITL 是人把关，护栏是规则把关：Prompt 注入检测、工具白名单、输出审核。

前置校验 + 白名单 + 输出过滤

为什么 3.3 之后必须来一课 HITL

  • 3.2/3.3 的 executor 输出的是处置方案文本——一旦接上真实的设备操作 API，Agent 的每一次幻觉都会变成一次生产事故
  • LLM 的诊断置信度再高也不是 100%：3.3 的 Loop 模式用 MAX_LOOPS 兜底时，会强制放行低置信度结论——这正是最需要人看一眼的时刻
  • 合规要求：运营商变更管理规范里，高风险操作必须有可追溯的人工授权记录——技术上就是 State 里那个 approval_status 字段

本实验的核心哲学

不是「让人审批一切」，而是「让人只审批值得审批的」。本实验只在 risk_level == "high" 时暂停——medium/low 直接执行。审批点设计得太宽，人会疲劳并变成无脑点「通过」，闸门就形同虚设；设计得太窄，等于没装。风险分级是 HITL 能否落地的前提，这也是 3.2 的 risk_router 在本实验里被复用的原因。

知识点一：interrupt() 不是异常，是「存档 + 把球抛回调用方」

langgraph.types.interrupt · Command(resume=...) · MemorySaver

三件事同时发生

当节点内调用 interrupt(payload)，LangGraph 会：① 把当前 State 序列化写入 checkpointer；② 把 payload 原样抛回给调用方（在 get_state().tasks[0].interrupts 里能取到）；③ 停止推进，get_state().next 指向被暂停的节点名。

三个必备条件，少一个就跑不通

  • 必须编译时传 checkpointer：graph.compile(checkpointer=MemorySaver())——没有存档处，暂停后的状态无处安放
  • 必须传 thread_id：config={"configurable":{"thread_id":"..."}}——恢复时必须用同一个 config，否则找不到那份存档
  • 必须从 langgraph.types 导入：from langgraph.types import interrupt, Command——它不是内置函数（本实验代码此前漏了这行，见排坑区）

恢复语义：节点整体重跑，不是从 interrupt 那一行继续

这是最容易误解的一点。Command(resume=...) 恢复时，LangGraph 从头重新执行整个节点函数，只是执行到 interrupt() 那一行时直接返回 resume 传入的值、不再暂停。所以 interrupt() 之前的所有代码都会跑第二遍。

实测坑：本实验的飞书通知会发两次

human_approval_node 在 interrupt() 之前生成 approval_id、写入 _pending、调 _notify_feishu()。resume 后节点重跑，这三件事又做一遍——飞书收到两张卡片，且第二次的 approval_id 是新 uuid，导致 _pending 里残留一条永远不会被消费的孤儿记录。修法：把副作用挪到 interrupt() 之后，或用 State 里已存在的 approval_id 做幂等判断。这也是「进阶挑战」的好素材。

# 关键：interrupt 和 Command 都来自 langgraph.types
from langgraph.types import Command, interrupt

def human_approval_node(state: HITLState):
    risk = state.get("risk_level", "medium")

    # 不到 high 不打扰人——审批疲劳是 HITL 头号杀手
    if risk != "high":
        return {**state, "approval_status": "auto_approved"}

    approval_id = str(uuid.uuid4())[:8]
    # 注意：这段在 resume 后会重复执行一次
    with _lock:
        _pending[approval_id] = {"event": threading.Event(), ...}
    _notify_feishu(approval_id, state)

    # ═══ 图在这里停住 ═══
    result = interrupt({
        "approval_id": approval_id,
        "device_id": state.get("device_id", ""),
        "risk_level": risk,
        "summary": state.get("decide_result", "")[:300],
    })

    # ↓ 只有 Command(resume=...) 之后才会走到这里
    approved = result.get("approved", False)
    return {**state,
        "approval_status": "approved" if approved else "rejected"}

知识点二：审批点插在「已经知道要做什么、但还没做」的位置

decider → risk_router → human_approval → executor

位置的讲究

审批点放在 decider 之后、executor 之前。太早（比如 detector 后）人手上没有诊断结论，无从判断；太晚（executor 后）操作已经下发，审批变成事后追认。「方案已成型、动作未发生」是唯一正确的介入时机。

和 3.2 的差别只有一处：多一个岔口

3.2 的 risk_router 把 high/medium/low 分流到三个不同的 executor；3.4 的 risk_router 把 high 分流到 human_approval，其余直连 executor。整张图只多了一个节点、改了一条条件边——Agent 节点完全没动，这是 LangGraph 编排与实现解耦的价值。

驳回不等于报错，是一条正常业务分支

human_approval 无论通过还是驳回，都照常走到 executor——由 executor 自己判断 approval_status：驳回则输出「方案已取消」而不调 LLM 生成方案。这样做的好处是流程有唯一出口，日志、埋点、State 终态都统一，不用为驳回单开一条通往 END 的边。

双重把关：节点内还有一道 risk 判断

注意 human_approval_node 开头又检查了一次 risk != "high" 并返回 auto_approved。条件边已经拦过一次，这里是防御性冗余——万一有人改图时把 medium 也连进来，节点自己不会误暂停。auto_approved 和 approved 是两个不同的值，审计时能区分「人批的」和「系统放的」。

def risk_router(state) -> Literal["human_approval", "executor"]:
    if state.get("risk_level") == "high":
        return "human_approval"
    return "executor"

graph.add_conditional_edges("decider", risk_router, {
    "human_approval": "human_approval",
    "executor":       "executor",
})
# 审批完（无论通过/驳回）都进 executor —— 唯一出口
graph.add_edge("human_approval", "executor")
graph.add_edge("executor", END)

CHANNEL 3 · 飞书 卡片按钮走 URL，不走回调

卡片两个按钮是 URL 链接，直接打开 :8100/approve/<id> 页面。为什么不用卡片回调？回调要求飞书服务器能 POST 到公网可达的地址，本地开发环境收不到。URL 模式零公网依赖。

讲师演示 · 需 feishu-server.py

Web 通道的关键设计：为什么要 Event 而不是轮询 State

Agent 流水线和 Flask 服务在不同线程/进程。LangGraph 的 interrupt 只把球抛给了「调用 stream 的那一方」，Flask 并不知道有人在等。_pending[approval_id] 这个共享字典就是两边的约会点：流水线侧写入并等 event.wait()，Web 侧按 approval_id 找到它、填结果、event.set()。approval_id（uuid 前 8 位）是关联两侧的唯一凭证——它同时出现在 interrupt payload、飞书卡片 URL 和 Web 页面表单里。

三条通道共享同一份 State，所以可以混用

  • 终端已经在等 input() 时，你仍然可以打开浏览器点通过——两条通道抢答，谁先到算谁的
  • 审批结果最终都收敛为同一个形状：{"approved": bool, "comment": str}，作为 Command(resume=...) 的入参
  • 节点内做了兼容：resume 值不是 dict 时按字符串处理（"y"/"yes"/"true" 视为通过），方便调试时直接传字符串

# ═══ 流水线侧：写入约会点 ═══
event = threading.Event()
with _lock:
    _pending[approval_id] = {"device_id": ..., "risk_level": risk,
                             "summary": ..., "event": event, "result": None}

# ═══ Flask 侧：找到约会点，填结果，唤醒 ═══
@app.route("/hitl/approve", methods=["POST"])
def hitl_approve():
    aid = request.get_json().get("approval_id", "")
    with _lock:
        info = _pending.get(aid)
    if not info:
        return jsonify({"error": "审批项不存在或已处理"}), 404
    info["result"] = {"approved": True}
    info["event"].set()          # ← 唤醒等待方
    return jsonify({"status": "ok"})

进阶挑战

  • 审批超时降级：5 分钟无人审批则自动驳回并发催办——注意别用 event.wait() 无超时版
  • 驳回意见回灌：把审批意见塞回 diagnoser_node 重新诊断，形成 3.3 Loop 模式的人机混合版
  • 两级审批：P0 需一线 → 二线两道闸门，两个 HITL 节点串联，注意 approval_id 不能撞
