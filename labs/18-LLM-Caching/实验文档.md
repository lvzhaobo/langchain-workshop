# Lab 18 · LLM Caching —— 相同查询不重复花钱

> lab 17 的 Callbacks 让你看到了每次调用的花费。但你很快会发现一个问题：同一台设备被反复分析，同一个排障问题被多次询问——每次都在重复花钱。本实验给 LLM 加上缓存层，相同查询直接返回缓存，零成本、零延迟。

---

## 🎯 实验目标

- 理解 LLM 缓存的三种粒度：精确匹配 / 语义匹配 / 混合
- 实现一个简易的 LLM 缓存层（精确匹配 + TTL 过期）
- 对比"有缓存"和"无缓存"的 Token 节省效果
- 接入平台：缓存命中时前端显示 🟢 "来自缓存" 标识

---

## 🏗️ 缓存放在哪

```
用户请求
    │
    ▼
┌──────────┐   命中   ┌──────────┐
│  缓存层   │────────→│ 返回缓存   │  零 Token、零延迟
│          │          │ 🟢 缓存命中  │
└────┬─────┘          └──────────┘
     │ 未命中
     ▼
┌──────────┐
│  LLM API  │  ← 正常调用，结果写入缓存
└──────────┘
```

缓存 Key = `(model, prompt)` 的哈希。相同 model + 相同 prompt → 直接返回缓存。

## 📦 标准路径

### 第一步：实现缓存层

```python
# cache_demo.py
import hashlib
import json
import time
from typing import Optional, Tuple


class SimpleLLMCache:
    """简易 LLM 缓存——精确匹配 + TTL 过期"""

    def __init__(self, ttl_seconds: int = 3600):
        """
        ttl_seconds: 缓存过期时间（秒），默认 1 小时
        """
        self._cache: dict = {}  # key → (timestamp, response)
        self.ttl = ttl_seconds
        self.hits = 0
        self.misses = 0

    def _make_key(self, model: str, messages: list) -> str:
        """根据 model + messages 生成缓存 key"""
        content = json.dumps({"model": model, "messages": messages}, ensure_ascii=False, sort_keys=True)
        return hashlib.sha256(content.encode()).hexdigest()

    def get(self, model: str, messages: list) -> Optional[str]:
        """查缓存，命中返回内容，未命中返回 None"""
        key = self._make_key(model, messages)
        if key in self._cache:
            timestamp, cached_response = self._cache[key]
            if time.time() - timestamp < self.ttl:
                self.hits += 1
                return cached_response
            # 过期，删除
            del self._cache[key]
        self.misses += 1
        return None

    def set(self, model: str, messages: list, response: str):
        """写入缓存"""
        key = self._make_key(model, messages)
        self._cache[key] = (time.time(), response)

    @property
    def stats(self) -> dict:
        total = self.hits + self.misses
        hit_rate = (self.hits / total * 100) if total > 0 else 0
        return {
            "命中次数": self.hits,
            "未命中次数": self.misses,
            "总查询次数": total,
            "命中率": f"{hit_rate:.1f}%",
            "缓存条目数": len(self._cache),
            "TTL（秒）": self.ttl,
        }

    def clear(self):
        """清空缓存"""
        self._cache.clear()
        self.hits = 0
        self.misses = 0
```

### 第二步：给 LLM 调用加上缓存

```python
from langchain_openai import ChatOpenAI

cache = SimpleLLMCache(ttl_seconds=1800)  # 30 分钟过期

def ask_llm_with_cache(prompt: str, model: str = "deepseek-chat") -> tuple:
    """带缓存的 LLM 调用。返回 (回答, 是否缓存命中)"""
    messages = [
        {"role": "system", "content": "你是 5G 基站排障专家助手。"},
        {"role": "user", "content": prompt},
    ]

    # 第一步：查缓存
    cached = cache.get(model, messages)
    if cached is not None:
        print(f"🟢 缓存命中！跳过 LLM 调用")
        return cached, True

    # 第二步：缓存未命中，正常调用 LLM
    print(f"🔴 缓存未命中，调用 LLM…")
    llm = ChatOpenAI(model=model, temperature=0, ...)
    response = llm.invoke(prompt)
    result = response.content

    # 第三步：写入缓存
    cache.set(model, messages, result)
    return result, False
```

### 第三步：对比实验——有缓存 vs 无缓存

```python
# 模拟场景：同一台设备被多个同事反复分析
REPEATED_PROMPT = """

- [P0] 基站退服：SCTP 链路中断导致退服

请给出排查步骤。
"""

# ── 第一轮调用 ──

result1, hit1 = ask_llm_with_cache(REPEATED_PROMPT)
print(f"{'🟢 缓存' if hit1 else '🔴 LLM'}: {result1[:100]}...")

print(f"{'🟢 缓存' if hit2 else '🔴 LLM'}: {result2[:100]}...")

print("\n=== 第 3 次查询（不同 Prompt）===")
```

## 🏗️ 进阶挑战

### 1. 语义缓存

当前是精确匹配——Prompt 差一个空格都不命中。改成语义缓存：对 Prompt 做 Embedding，相似度 > 0.98 的两个 Prompt 视为同一查询，返回缓存的回答。

### 2. 分层缓存

```
L1: 内存缓存（TTL 10 分钟）→ 最快
L2: 磁盘缓存（TTL 24 小时）→ 重启不丢
L3: LLM API → 兜底
```

### 3. 缓存预热

构造 10 条高频排障问题（如"AAU5613 退服怎么处理""光模块告警怎么排查"），在系统启动时预加载到缓存——第一次用户询问就是 🟢 命中。

## ⚠️ 常见问题

| 问题 | 原因 | 解决方法 |
|------|------|---------|
| 相同 Prompt 不命中 | JSON 序列化时 key 顺序不一致 | `json.dumps(..., sort_keys=True)` |
| 缓存命中但返回陈旧数据 | TTL 设置太长 | 根据数据新鲜度要求调 TTL |
| 缓存占用内存太大 | 缓存条目过多 | 加 `max_size` 限制，LRU 淘汰旧条目 |
| 缓存让"实时查询"变脏 | 设备数据变了但缓存没失效 | 设备变更时主动清相关缓存 |
