# Lab 28 · LangSmith 追踪

> Lab 25 教的是「自己写 callback 打点」。这一节讲**不用写**的那条路，以及什么时候该自己写。

## 两种模式都能跑

```bash
./run.sh 28
```

| 有没有 `LANGSMITH_API_KEY` | 行为 |
|---|---|
| 没有 | 用本地记录器打出**同样结构**的 run tree，看清"LangSmith 会收到什么" |
| 有 | 真实上报到 smith.langchain.com，控制台能看到完整调用链 |

**没配 key 也能跑**，这是这个 lab 的刻意设计——先看懂结构，再决定要不要注册。

## 接真实 LangSmith

```bash
# 写进 .env
LANGSMITH_API_KEY=lsv2_pt_xxx
LANGSMITH_PROJECT=langchain-workshop
```

重跑本实验，然后打开 https://smith.langchain.com 就能看到这次运行的完整 run tree。

> LangSmith 的免费额度对个人学习够用（每月 5000 次 trace），企业版才收费。

## 一次诊断产生 5 个 span

```
trace                        kind            耗时  属性
diagnose_chain             chain       2457ms  device_id=DEV-0001
  fetch_device               tool          55ms  device_id=DEV-0001
  search_kb                  retriever     32ms  query=SCTP 链路中断
  llm_call                   llm         2369ms  model=deepseek-chat
  parse_output               parser         0ms
────────────────────────────────────────────────────────────
总耗时 2457ms  |  5 个 span
```

**这就是 LangSmith 的价值**：你什么都没写，但能立刻看出
「2.4 秒里 2.37 秒花在 LLM 上，两个工具加起来不到 100ms」——
优化方向一目了然。

## 和 Lab 25（自写 callback）的取舍

| | 自写 Callback（Lab 25） | LangSmith（本节） |
|---|---|---|
| 接入成本 | 要写几十行 handler | 三个环境变量 |
| 采集什么 | 你说了算 | 框架自动采集 |
| 跨服务 | 串不起来 | 能串（同一个 trace 跨多个进程/服务） |
| 数据位置 | 全在本地 | 上传到云端 |
| 适合 | 已有内部监控体系，只补几个指标 | 快速定位问题、小团队 |

**生产建议**：先上 LangSmith 把问题找出来，再决定哪些指标值得自己埋点。
反过来（先自己造一套）通常会把精力花在造轮子上。

## 打卡内容

1. 本地 run tree 的截图（5 个 span）
2. 哪个 span 最慢，占总耗时多少
3. （有 key 的话）LangSmith 网页里的 trace 截图

## 常见问题

| 现象 | 原因 | 解 |
|---|---|---|
| 跑完网页里什么都没有 | 环境变量没生效 | 确认 `LANGSMITH_API_KEY` 在 `.env` 里且被 load_dotenv 读到 |
| 项目名找不到 | 默认项目和预期不一致 | 显式设 `LANGSMITH_PROJECT` |
| 老版本变量名不生效 | 1.x 用 `LANGSMITH_*`，旧版是 `LANGCHAIN_*` | 两套都认，本 lab 都查了 |
