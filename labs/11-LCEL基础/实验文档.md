# Lab 11 · LCEL 基础 — 管道 + 容错

> LCEL 没有魔法，就两样东西：**① `|` 管道符** — 上一步输出自动成为下一步输入；**② 容错方法** — `.with_fallbacks()` 降级、`.with_retry()` 重试。价值不在功能多（普通 Python 也能写），而在统一接口——换模型、换 Parser、加降级都不改调用方式，全用 `.invoke()`/`.stream()`。


## 🎯 实验目标

- 理解 `|` 管道符：一切皆 Runnable，上一步输出 → 下一步输入
- 用 `RunnableParallel` 并行跑三条链，实测耗时 ≈ max(最慢那条)
- 掌握 `.with_fallbacks()`：主挂了自动切备用
- 掌握 `.with_retry()`：抖一下再试，分清"重试"和"降级"是两类问题

---

## 四块基本功

```
① 基础链       prompt | llm | parser              （积木怎么拼）
② 并行         RunnableParallel(诊断, 工单, 风险评分)（三条链同时跑）
③ 降级         broken_llm.with_fallbacks([backup])  （主挂了切备）
④ 重试         step.with_retry(stop_after_attempt=3)（抖一下再试）
```

---

## 📦 运行

```bash
python lcel_basics.py
```

四个部分依次演示，终端能看到每步的结果。

### ① 基础链 — `|` 到底在干什么

```python
basic_chain = diagnose_prompt | llm | StrOutputParser()
#              ↑ dict → 消息      ↑ 消息 → AIMessage   ↑ AIMessage → str

result = basic_chain.invoke({"device_info": "..."})
```

每一步的输出类型就是下一步的输入类型——这是 LCEL 唯一需要记住的规则。

### ② RunnableParallel — 诊断 + 工单标题 + 风险评分一次出

```python
parallel_chain = RunnableParallel(
    diagnosis=diagnose_prompt | llm | StrOutputParser(),
    ticket_title=ticket_prompt | llm | StrOutputParser(),
    risk_score=risk_prompt | llm | StrOutputParser(),
)
```

重点看输出里的耗时对比——并行 ≈ max(最慢那条)，串行 = 三条之和。

### ③ with_fallbacks — 主模型故障自动切备用

脚本故意给主模型配了**无效 API Key** 模拟故障：

```python
broken_llm = ChatOpenAI(api_key="sk-invalid-...")
llm_with_fallback = broken_llm.with_fallbacks([backup_llm])
```

主模型抛 401 → 自动走备用 → 用户拿到的回答正常，全程无感知。

### ④ with_retry — 瞬时抖动 ≠ 宕机

```python
RunnableLambda(flaky_step).with_retry(
    retry_if_exception_type=(ConnectionError,),
    stop_after_attempt=3,
)
```

`flaky_step` 前 2 次抛异常、第 3 次成功——模拟网络抖动。

| | 重试 | 降级 |
|--|------|------|
| 适用故障 | 瞬时（网络抖动、限流） | 持续（服务宕机、Key 失效） |
| 代价 | 加时延 | 换模型 |
| 生产惯例 | 先重试 2-3 次，耗尽再降级 | — |

## ⚠️ 常见问题

| 问题 | 原因 | 解决 |
|------|------|------|
| 主备都失败 | 备用模型用的是 `AGENT_API_KEY` 没配 | 检查 `.env` |
| 并行提速不明显 | 两条链耗时差大，短的等长的 | 正常，看串行对照 |
| with_retry 不生效 | 异常类型不匹配 | 检查 `retry_if_exception_type` |
