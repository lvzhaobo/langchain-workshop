01

知识点①：StateGraph 三要素

TypedDict State · Node = 函数 · Edge = 路由 · Reducer

心智模型

一张图 = 一份共享 State（TypedDict）+ 若干节点（普通 Python 函数，入参是 State、返回更新后的 State）+ 边（决定下一步去哪）。invoke 后引擎从入口节点出发，沿边执行到 END——State 像接力棒，在节点间传递并不断被写入新字段。

本实验的 State 设计

  • 输入区：user_input / device_id —— 用户说了什么、查哪台设备
  • 产出区：detect / diagnose / decide / execute_result —— 四个节点各写各的字段，互不覆盖
  • 控制区：risk_level / next_step —— 流程控制字段，条件边靠它路由
  • 日志区：messages 配 operator.add reducer —— 追加而非覆盖，留下完整协作轨迹

关键认知

一份 State 定义，三种模式复用。模式的差异不在节点、不在 State，只在边怎么连——这正是「流程编排」与「业务逻辑」解耦的价值。

02

知识点②：单 Agent 拆成四个子 Agent

detector · diagnoser · decider · executor · 各管一段

为什么要拆

3.1 的 troubleshoot 通道是一个 Prompt 干四件事：查状态、找根因、评风险、给方案。Prompt 越长模型越容易顾此失彼。拆成四个 Node 后，每个节点只有一个职责、一个专注的 System Prompt——检测节点只说"你是检测工程师"，处置节点只说"你是排障执行专家"。

拆分的三个工程收益

  • 产出可检查：每个节点的结果写进独立的 State 字段，终端能看到四段清晰的产出，而不是混在一起的一大段话
  • Prompt 可单独调优：诊断不准就只改 diagnoser 的 Prompt，不影响其他三个
  • 节点可复用：同一组节点函数，三种模式直接复用——只换连边方式

数据从哪来

detector 调平台 API（:8000/devices，Day 1 产物）拿真实设备数据；diagnoser 用 FAISS 知识库（2.1 产物）做 RAG 检索——知识库没建好时自动降级为通用排障知识，实验不会卡死。

03

知识点③：三种协作模式——差异全在「边」上

serial 固定边 · supervisor 条件边 · conditional 风险分流

模式一 · 串行流水线（最简单）

全是固定边——铁轨，没有岔路口。add_edge("A","B") 表示 A 完成后一定去 B。适合流程固定、步骤明确的排障 SOP："基站退服排查"永远是检测 → 诊断 → 决策 → 处置，不会跳步。

graph = StateGraph(AgentState)

graph.add_node("diagnoser", diagnoser_node)
graph.add_node("decider", decider_node)
graph.add_node("executor", executor_node)

graph.set_entry_point("detector")
graph.add_edge("detector", "diagnoser")  # 铁轨
graph.add_edge("diagnoser", "decider")
graph.add_edge("decider", "executor")
graph.add_edge("executor", END)

模式二 · Supervisor 调度（最灵活）

把固定边换成条件边：每个节点完成后不直接去下一站，而是交给 supervisor_router 函数看 State 重新决策——哪个产出字段还是空的，就派活给对应节点；全齐了返回 __end__ 收工。

和串行的关键差异

  • 串行：add_edge("A","B") → A 完成后一定去 B
  • Supervisor：add_conditional_edges("A", router, {...}) → A 完成后由 router 决定去哪
  • 流程简单时两者结果几乎一致；当需要"诊断置信度低 → 回退重新检测"时，只改 router 一个函数就能实现——串行做不到
supervisor_router() — 按 State 进度派活
def supervisor_router(state: AgentState):
    if not state.get("detect_result"):
        return "detector"   # 还没检测→去检测
    if not state.get("diagnose_result"):
        return "diagnoser"
    if not state.get("decide_result"):
        return "decider"
    if not state.get("execute_result"):
        return "executor"
    return "__end__"       # 全部完成

graph.add_conditional_edges("detector",
    supervisor_router, {"diagnoser": "diagnoser",
                        "__end__": END})

模式三 · 条件分支（最精准）

生产环境更常见的诉求："高风险走紧急通道、低风险走常规通道"。前三步照旧串行，decider 之后按 State 里的 risk_level 分流到三个不同的 executor——高风险方案自动标注"建议人工审批"，低风险只给例行巡检建议（省 LLM 调用）。这是 1.7 RunnableBranch 的 StateGraph 版。

risk_router() — 按风险等级分流
def risk_router(state: AgentState):
    risk = state.get("risk_level", "medium")
    if risk == "high":
        return "executor_high"   # 紧急+审批
    elif risk == "low":
        return "executor_low"    # 例行巡检
    return "executor_normal"

# decider 之后不是固定边，而是条件路由
graph.add_conditional_edges("decider",
    risk_router, {
    "executor_high":   "executor_high",
    "executor_normal": "executor_normal",
    "executor_low":    "executor_low"})

一个隐藏细节

risk_level 是 decider 节点用关键词匹配从 LLM 输出中提取的（匹配 【风险等级】：high）——LLM 输出格式一变就会提取失败退回默认值 medium。更稳的做法是 3.1 学过的 PydanticOutputParser 结构化输出，这是进阶挑战之一。

VS

三种模式怎么选？

复杂度 vs 灵活性 · KISS 原则优先
对比维度Serial 串行Supervisor 调度Conditional 分支
复杂度最低中等中等
灵活性无——固定顺序最高——每一步可跳转/回退中等——只在分支点灵活
边的写法add_edge 固定边每个节点接 conditional_edges + router串行 + 分支点一处 conditional_edges
适合场景流程固定、无例外的排障 SOP复杂任务调度、需要动态调整流程分级处置——不同情况不同处理
与前面实验的关系1.7 RunnableBranch 的升级版3.1 意图路由的 StateGraph 实现1.4 Agent 的条件路由版

选型口诀

流程固定 → serial（KISS 原则，别为了灵活而灵活）；需要动态调度 → supervisor；根据结果分流 → conditional。另外记住：调度本身也是开销，多 Agent = 更多 LLM 调用 = 更贵更慢，拆之前先算 ROI（进阶挑战 3 会让你实测 Token 消耗对比）。
