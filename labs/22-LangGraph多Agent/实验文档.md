# Lab 22 · LangGraph 多 Agent 流水线 —— 从串行到 Supervisor 到条件分支

> lab 21 的意图路由把用户问题分到了正确的通道。但每个通道里还是一个 Agent 干所有事——检测、诊断、决策、处置全塞在一个 Prompt 里。本实验把**单个通道拆成四个子 Agent**，用 LangGraph StateGraph 编排它们协作。三种模式，同一个任务，看清差异。

---

## 🎯 实验目标

- 理解 LangGraph 的三要素：State / Node / Edge
- 同一个排障任务，用三种协作模式各跑一遍：
  - **串行流水线**：固定顺序，无条件分支（最简单）
  - **Supervisor 调度**：中央路由函数决定每一步走向（最灵活）
  - **条件分支**：根据风险等级动态选择不同的处置通道（最精准）
- 对比三种模式的耗时、灵活度、适用场景

---

## 🏗️ 从 3.1 到 3.2：单 Agent 变多 Agent

```
lab 21（意图路由后）                lab 22（本实验）
─────────────────                   ─────────────

troubleshoot 通道                    拆为四个子 Agent：
  │                                   ┌──────────┐
  └→ 一个 Agent                        │ detector  │  查设备状态 + 列出告警
      做所有事                         ├──────────┤
                                      │ diagnoser │  搜知识库 + 定位根因
                                      ├──────────┤
                                      │ decider   │  评估风险 + 决定策略
                                      ├──────────┤
                                      │ executor  │  生成方案 + 输出建议
                                      └──────────┘
```

核心变化：一个 Prompt → 四个独立 Node，每个 Node 有自己专注的 System Prompt。

## 📦 标准路径

### 第一步：理解 StateGraph 三要素

```python
from typing import TypedDict
from langgraph.graph import StateGraph, END

# 1) State：所有子 Agent 共享的数据结构
class AgentState(TypedDict):
    user_input: str            # 原始输入
    detect_result: str         # 检测节点的产出
    diagnose_result: str       # 诊断节点的产出
    decide_result: str         # 决策节点的产出
    execute_result: str        # 处置节点的产出
    risk_level: str            # 流程控制字段——决定走哪条分支
    next_step: str             # Supervisor 用——决定下一步调谁

# 2) Node：每个子 Agent 是一个函数，输入 State，输出更新后的 State
def detector_node(state: AgentState) -> AgentState:
    # 查设备 API，分析告警
    ...
    return {**state, "detect_result": "检测完成..."}

# 3) Edge：Node 之间的连接
graph = StateGraph(AgentState)
graph.add_node("detector", detector_node)
graph.add_node("diagnoser", diagnoser_node)
graph.add_edge("detector", "diagnoser")  # 固定边：detector 完成 → 一定走 diagnoser
```

### 第二步：模式一——串行流水线（固定顺序）

最简单的多 Agent 编排：A → B → C → D，没有条件、没有分支。

```python
def build_serial_pipeline():
    graph = StateGraph(AgentState)
    graph.add_node("detector", detector_node)
    graph.add_node("diagnoser", diagnoser_node)
    graph.add_node("decider", decider_node)
    graph.add_node("executor", executor_node)

    # 全是固定边——铁轨，没有岔路口
    graph.set_entry_point("detector")
    graph.add_edge("detector", "diagnoser")
    graph.add_edge("diagnoser", "decider")
    graph.add_edge("decider", "executor")
    graph.add_edge("executor", END)

    return graph.compile()
```

**适用场景**：流程固定、步骤明确的排障 SOP。"基站退服排查"就是检测 → 诊断 → 决策 → 处置，不会跳步。

### 第三步：模式二——Supervisor 调度（中央路由）

在串行基础上加一层"调度器"——`supervisor_router` 函数根据 State 的当前状态决定下一步。每个 Node 完成后不是走固定边，而是回到 Supervisor 重新决策。

```python
def supervisor_router(state: AgentState):
    """Supervisor：根据当前进度决定下一步"""
    if not state.get("detect_result"):
        return "detector"       # 还没检测 → 去检测
    if not state.get("diagnose_result"):
        return "diagnoser"      # 还没诊断 → 去诊断
    if not state.get("decide_result"):
        return "decider"        # 还没决策 → 去决策
    if not state.get("execute_result"):
        return "executor"       # 还没处置 → 去处置
    return "__end__"            # 全部完成


def build_supervisor_pipeline():
    graph = StateGraph(AgentState)
    graph.add_node("detector", detector_node)
    graph.add_node("diagnoser", diagnoser_node)
    graph.add_node("decider", decider_node)
    graph.add_node("executor", executor_node)

    graph.set_entry_point("detector")

    # 每个节点完成后走 conditional_edges → supervisor_router 重新决策
    graph.add_conditional_edges("detector", supervisor_router, {
        "diagnoser": "diagnoser", "__end__": END,
    })
    graph.add_conditional_edges("diagnoser", supervisor_router, {
        "decider": "decider", "__end__": END,
    })
    # ... 其他节点同理
```

**和串行的关键差异**：
- 串行：`add_edge("A", "B")` → A 完成后**一定**去 B
- Supervisor：`add_conditional_edges("A", router, {...})` → A 完成后**由 router 决定**去哪

### 第四步：模式三——条件分支（根据诊断结果分流）

Supervisor 按进度路由，但实际生产环境更常见的需求是："高风险走紧急通道，低风险走常规通道"。这就需要条件分支——根据 State 中的 `risk_level` 字段选择不同的 executor。

```python
def risk_router(state: AgentState):
    """根据风险等级，走不同的处置通道"""
    risk = state.get("risk_level", "medium")
    if risk == "high":
        return "executor_high"     # 高风险 → 紧急处置 + 人工审批
    elif risk == "low":
        return "executor_low"      # 低风险 → 例行巡检
    return "executor_normal"       # 中等风险 → 标准处置


def build_conditional_pipeline():
    graph = StateGraph(AgentState)
    # ... detector / diagnoser / decider 照常 ...

    # 三个不同的 executor
    graph.add_node("executor_high", executor_high_risk)
    graph.add_node("executor_normal", executor_node)
    graph.add_node("executor_low", executor_low_risk)

    # 关键：decider 之后不是固定边
    graph.add_conditional_edges("decider", risk_router, {
        "executor_high": "executor_high",
        "executor_normal": "executor_normal",
        "executor_low": "executor_low",
    })
```

### 第五步：运行对比

python supervisor_pipeline.py conditional

同一个任务（"DEV-0001 SCTP链路中断导致退服，帮我排查"），三种模式各跑一遍，观察终端输出。注意对比——串行和 Supervisor 在流程简单时结果几乎一致，但当"诊断结果不确定需要回退到检测重新查"时，Supervisor 的优势才会体现。

### 第六步：三种模式对比总结

| 对比维度 | Serial | Supervisor | Conditional |
|---------|:--:|:--:|:--:|
| 复杂度 | 最低 | 中等 | 中等 |
| 灵活性 | 无——固定顺序 | 最高——每一步可跳转 | 中等——只在分支点灵活 |
| 适合场景 | 流程固定、无例外 | 需要动态调整流程 | 不同情况不同处理 |

## ⚠️ 常见问题

| 问题 | 原因 | 解决方法 |
|------|------|---------|
| `add_conditional_edges` 报 KeyError | 路由函数返回的 key 在目标字典中不存在 | 对照 `{返回值: Node名}` 映射，确保一致 |
| Supervisor 无限循环 | router 函数有 bug，永远不返回 `__end__` | 加 step counter，超过 10 步强制 END |
| 条件分支没按预期分流 | `risk_router` 的判断逻辑不准 | 在 decider_node 中打印 `risk_level` 确认值 |
| 四个 Node 的输出太相似 | System Prompt 区分度不够 | 每个 Node 的 Prompt 有明确的"输入是什么、产出是什么" |
| State 字段在 Node 间丢失 | `{**state, "key": val}` 要确保展开原 state | 检查每个 Node 的 return 是否包含 `**state` |
